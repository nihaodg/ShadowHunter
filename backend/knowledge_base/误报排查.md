# 误报排查（安全设备告警 ≠ 失陷）

应急响应里有一大类是「告警了，但主机其实没事」。**先做误报排查，再定性失陷**，这是专业和业余的分水岭。

## 高频误报场景

### 1. DNS 服务器解析恶意域名

- **现象**：天眼/态势感知报 DNS 服务器「命令执行」「代码执行」告警
- **真相**：内网服务器/PC 访问恶意域名，DNS 服务解析该域名 → 触发告警，DNS 服务器本身干净
- **排查**：上机排查计划任务（告警内容里是日志易的计划任务，正常）、历史命令、外连 IP、挖矿进程，均无异常 → 误报

### 2. SMB 异常登录（Exchange DAG）

- **现象**：青藤云报大量 SMB 登录告警，每分钟一次
- **真相**：Exchange DAG 服务利用 SMB 访问共享文件做邮件服务器故障监控，触发新告警规则
- **排查**：无异常进程；共享文件夹路径特征（C:\DAGFileShareWitnesses\）和命名格式判断是 DAG 默认文件夹

### 3. 漏扫工具脏数据 / 覆盖账号

- **现象**：漏扫后 admin 账号无法登录、数据库有脏数据
- **真相**：漏扫工具触发注册接口（id 参数赋 1）覆盖了 admin 账号信息
- **排查**：日志确认来源 IP 是漏扫地址，接口本身有鉴权但注册接口设计缺陷

### 4. EDR 规则更新后暴露历史残留

- **现象**：装了新 EDR 后突然大量告警（反弹 shell、webshell）
- **真相**：历史演习/入侵留下的计划任务/webshell，之前没 EDR 所以没告警
- **排查**：回溯计划任务创建时间 ↔ 历史演习时间，对比历史应急报告

### 5. 远控告警 MAC 不一致

- **现象**：Gh0st 远控告警指向某服务器
- **真相**：告警主机的 MAC 与数据包 MAC 不一致，真源是别的终端
- **排查**：核对 MAC、hosts 改 127.0.0.1 后是否仍告警、排查主机无入侵痕迹

## 误报排查通用思路

1. **核对告警元数据**：MAC、源 IP、告警规则更新时间
2. **上机排查全项**：进程/网络/账号/计划任务/历史命令，逐项确认「无异常」
3. **找替代解释**：告警行为是否有正常业务对应（DNS 解析、SMB 心跳、DAG 共享、漏扫）
4. **回溯时间线**：告警行为 ↔ 历史事件（演习/入侵残留）

## 报告要点

- 明确结论：**未发现失陷，属误报/正常业务/历史残留**
- 说明排除依据（逐项排查结果 + 误报原因解释）
- 建议：若再告警第一时间排查、封禁恶意域名（即使误报也建议封恶意域名/IP）

## 真实案例速记

- **中华财险 DNS**：DNS 服务器告警命令执行/代码执行，实为内网访问 miges.myloglist.top 恶意域名触发解析，DNS 服务器本身正常。
- **国金基金 SMB**：Exchange DAG 故障监控触发 SMB 告警，属正常行为（新规则误报）。
- **中国农大 admin 丢失**：漏扫工具触发注册接口覆盖 admin，非恶意攻击。
- **昆仑数智 Gh0st**：远控告警，排查大数据服务器无异常（MAC 不一致），疑点指向个人终端。
