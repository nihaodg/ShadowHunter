# 反序列化漏洞利用应急响应

## 事件特征（分诊依据）

- 大量反序列化/命令执行告警（Shiro/Java）
- 攻击者先向 dnslog 服务器请求（验证漏洞）
- 存在默认 key（Shiro 默认 key）
- WAF 拦截记录里有反序列化 payload
- 反弹 shell 到公网 IP

## 排查要点

1. **漏洞确认（不实际攻击）**：验证系统是否存在 Shiro 默认 key —— **确认存在即可，不进行实际攻击/利用**。
2. **攻击行为分析**：
   - 攻击者先请求 dnslog 验证漏洞
   - 随后反弹 shell 到互联网服务器（如 140.143.196.77:50001）
   - WAF 拦截记录
3. **history 记录**：查被攻击服务器的 history，看攻击者是否拿到权限后执行了命令。
4. **影响范围**：同一组件/默认 key 是否影响其他系统（如 cms.heromutual.com 和 cms2.heromutual.com 都有默认 key）。

## 典型攻击路径

```
Shiro 默认 key（反序列化前提）
  → 攻击者向 dnslog 请求验证
  → 构造反序列化 payload 命令执行
  → 反弹 shell 到公网服务器
```

## 处置建议

1. **封禁攻击 IP**（业务影响广时先封 IP）
2. 修改 Shiro 默认 key（不影响业务的前提下）
3. 联系开发确认打补丁/升级 Shiro 版本
4. 重点关注该系统告警监控，再次告警第一时间排查
5. 定期漏洞扫描、全盘查杀、数据备份

## 报告要点

- 事件分析：漏洞确认（默认 key 存在）、攻击时间线（dnslog → 反弹 shell）、WAF 拦截记录
- 总结：定性「存在 shiro 默认 key = 反序列化利用前提」，明确「未实际攻击」
- 建议对应根因：Shiro 默认 key、组件版本旧

## 真实案例速记

- **汇友财险**：腾讯云监控发现 IP 106.37.182.211 对 cms.heromutual.com 进行 Shiro 反序列化攻击，先请求 dnslog，后反弹 shell 到 140.143.196.77:50001。工程师验证系统存在 shiro 默认 key（未实际攻击），cms2.heromutual.com 同样存在。处置：封 IP + 建议改默认 key。
