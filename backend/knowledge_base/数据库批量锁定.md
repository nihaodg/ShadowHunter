# 数据库批量锁定 / 业务中断应急响应

## 事件特征（分诊依据）

- 生产数据库大量用户被锁定，业务大面积中断
- 大量重连爆破告警（其实是应用自动重连）
- 数据库用户锁定机制被触发

## 排查要点

1. **区分「攻击目标」与「告警表象」**：大量重连爆破告警的产生原因是**数据库用户被锁，应用系统自动尝试重连**，不是真爆破。信息中心指出的「异常主机」不一定是真攻击源，要排查实际被攻击系统。
2. **定位真实攻击源**：排查 webshell、漏洞接口、攻击者上传的爆破工具。
3. **漏洞接口排查**（任意文件读写/脚本执行组合拳）：
   - 任意文件读取接口（读 /root/nginx-reload.sh）
   - 任意文件写入接口（写 webshell）
   - 触发执行脚本接口（nginxReload 触发 /root/nginx-reload.sh）
4. **webshell 与工具落地**：root 路径删除 inbex.jsp 的脚本、下载 gonc（p2p 隧道代理）、上传 java 爆破工具 boracle.class + 用户名字典。
5. **关键证据链**：上传的**用户名字典解码后刚好对应被锁定用户列表** → 证明爆破行为导致锁定。
6. **溯源**：nginx 反代日志确认攻击者 IP，比对攻击队信息。

## 典型攻击路径

```
供应链 0Day 漏洞（应用系统）
  → 分段写入 webshell（利用任意文件读写+脚本执行）
  → 获取服务器控制权限
  → 上传爆破工具 + 用户名字典
  → 暴力破解公共 Oracle 数据库
  → 触发用户锁定机制 → 大量业务中断
```

## 处置建议

1. 下线受影响系统 + 漏洞整改
2. 应用控制：禁非授权程序在 opt/tmp 等目录运行
3. 部署 EDR/XDR + 行为监控
4. 数据库侧：登录失败锁定策略、弱口令整改
5. 封禁攻击 IP

## 报告要点

- 事件分析要讲清「重连爆破是表象，真实原因是数据库被爆破锁定」
- 关键证据：字典文件 ↔ 锁定用户列表对应、webshell 写入时间线
- 总结给攻击队违规攻击行为定性（非演练范围单位）
- 建议对应根因：供应链 0Day、数据库弱口令

## 真实案例速记

- **教育部经费中心**：信息中心指出的异常主机非真攻击源。真实被攻击系统为捐赠配比系统，攻击者利用任意文件读取/写入/脚本执行组合拳（/donation/api/flow/action/ 接口）分段写 webshell，下载 gonc 隧道工具，上传 boracle.class 爆破工具，字典解码对应锁定用户，触发 Oracle 锁定导致业务中断。溯源大连理工大学攻击队（175.162.12.29 等 IP）。
